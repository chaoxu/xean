# Development workflow

## Current-only literature contract

The literature role is a thin Codex-backed note producer. Its output is
`{notes: [{text, support}]}` and is delivered through the ordinary submitted
note path. Coordinators, Explorers, and verifiers consume the resulting notes;
they do not receive a separate literature report or retrieval context. A
literature note is untrusted until the normal correctness and source checks
establish it. Keep external retrieval and source inspection at this service
boundary; the kernel remains unaware of the network.

This repository supports only the current role and journal schemas. Do not add
compatibility readers, migration branches, or legacy output formats. Add tests
only for a contract or failure that would otherwise be easy to regress; prefer
one focused boundary test over broad tests that mirror implementation details.

## Simplicity invariant

Use the vocabulary in [`../../docs/terms.md`](../../docs/terms.md) for every schema field, prompt, document, and identifier. Do not introduce a new term or a synonym; when a change needs a new concept, add its entry there in the same change.

`xean-solve` has one durable workflow. A task is one JSON object with `problem` and `completionCriteria`. `init TASK.json CAMPAIGN.db SETTINGS.json` creates or matches its declaration without provider setup or model calls. `run` takes the same arguments and starts or resumes that workflow. `inspect CAMPAIGN.db` derives its phase and terminal result from the journal.

Turn allowances are local journal calls, outside the frozen settings. Fresh `init` and `run` default to ten turns, overridden by `--turns N`. `run --turns N --id ID` grants an exhausted campaign another allowance and resumes it. Reusing the ID and count cannot grant it twice. New allowances require `turn-limit`, and accepted campaigns stay accepted. The runner lock fences allowance changes and execution. Inspection exposes the effective `maxExplorerTurns` and allowance receipts from its captured journal boundary. Completed checks and all historical entries retain their authority. Workflow schema is 19, execution-contract schema is 2, and execution reports retain schema 1.

Support only the current workflow declaration and execution contract. Change the workflow schema version when its stored format or the meaning of recorded evidence changes, including verifier policy changes. Prompt wording edits alone do not require a bump. Change the execution contract when its report shape or meaning changes. Notes may carry external `verification`, and an accepted result may have zero Explorer turns when a submitted proof passes all normal checks. Standalone role commands exercise the same typed boundaries and are not a second workflow. Xean Lab must derive a worker result from `inspect.result`, not trust solver stdout as a second authority.

Send changing task directions, coordinator guidance, continuation prompts, and correction requests as user messages. Keep stable role definitions and contracts in system/developer instructions, and factual results or validation errors in tool receipts. Inspect the constructed provider payload when checking this boundary; a field or helper name alone does not establish the message role.

Every Explorer call uses the submission gate and submits `{notes, solution}`. `maxExplorerResponses` defaults to 4 non-error model responses per call, including the first, allowing at most three continuations, and sets the gate's `maxResponses`. A value of 1 permits at most one non-error response, which must contain a valid submission to hand off. Plain text, length-limited output, and rejected submissions count. Provider errors use the separate recovery allowance. Internal provider retries share the response count; fresh role calls after failure or interruption start a fresh budget. Freeze the response budget with the settings and request. Its total-context budget defaults to 400,000 tokens, bounded by model capacity, and `explorerContextBudgetTokens` may override it. Reserve the model's maximum output tokens for finalization. A claimed complete solution or the first empty notes array hands off immediately. Other valid nonterminal submissions continue in the same call while responses remain and below the estimated context threshold. The tool receipt carries the actual result `{noteIds}` only; after the receipt, the Explorer receives a fresh user message exactly `Keep trying, you can do it.`. Explorer chooses the route; a plan or recap alone is insufficient. The message stays in the same context and requires no separate planning submission. At either the response budget or context threshold, a valid submission hands off all saved notes. Response exhaustion without a valid final submission fails the call. An empty submission hands off already saved work and the coordinator receives `emptySubmission: true` asking for a different promising approach. The Explorer gate sets `emptyArgument: "notes"` to stop empty-submission loops. This consumes one ordinary Explorer turn and grants no verification status. The validated tool-call record is durable even without its receipt or outer call-result. Inspection includes saved notes during active and failed calls. A fresh call after interruption receives those notes in full with stable IDs and the turn's frozen guidance. Mathematical verification retains its authority. Reuse Pi's native steering, terminal-tool results, and output caps. Pi infers `stopAfterToolResult: true` when `submissionGate` is supplied, and the normalized journal request retains that field. Keep coordinator and verifier execution in the existing workflow, and distinguish estimated context from billed reasoning usage.

`explorerGuidance` is fallible advice for the next turn, never a persistent setting or a replacement for the original task. Combine the coordinator's submitted guidance and pending external advice in that single Explorer input field. Reuse the coordinator's settled submission instead of copying it to another record. External advice is consumed once per Explorer turn, including all retries of that turn.

Submitted guidance and Explorer input boundaries use ordinary kernel calls in the campaign database. `guide` records advice without driving the workflow or changing terminal results. Guidance inspection is opt-in. Keep the `run` command and execution-report contract unchanged when only role schemas change.

`submit` appends caller-supplied text notes through ordinary local kernel calls, with no model role or provider request. Preserve each text exactly. String support IDs name existing campaign notes that are not dead. A positive integer names an earlier note in the same submission, counted from 1. Resolve these local references when delivery assigns actual note IDs, after any active Explorer output. Reject self references, forward references, duplicates, and missing existing support before appending. Preserve separate theorem notes and their edges when transferring work; concatenating a closure with empty support loses those dependencies. Freeze delivery before the next available coordinator input. Frozen role inputs and terminal results stay unchanged. Submission receipts and delivery are exposed only with `inspect --include-submissions`.

Verification runs correctness, source, requirements, reconstruction. Correctness reads the complete proof and support, checks declared dependencies and theorem applications, and lists each note's exact nonroutine external premises in `externalResults`. All verifiers and the independent final review allow PASS for local mistakes whose exact corrections they explicitly verify in the existing report, preserving the asserted result, task hypotheses, computational model, and bounds. Notes remain unchanged. Substantial gaps or undemonstrated repairs fail. A correctness PASS is conditional on source validation; an isolated cited theorem note can reach source verification, while an undeclared substantive application fails. Source reads only notes with assigned external premises, omitting supporting proofs. An empty premise list records a local source PASS bound to that exact correctness call and candidate, with no inference. Other source checks use Codex with web search. Source and independent-review profiles contain only `{model, reasoning}`. Freeze mandatory web search as `search: true` in each Codex request. Each nonroutine external result must be checked against an inspected primary-source passage. The source packet assigns a stable ID to each correctness premise; source passages bind to that ID, while the journal restores the exact assigned premise text. Earlier recorded PASS passages from completed source calls in the same campaign may be reused only for an exact assigned-result ID and with call/note provenance; the current source call still checks applicability. A result without browsing may cite only identical supplied passages. Source cannot omit or weaken assigned premises. A source mismatch fails only when it exposes a mathematical defect or unsupported required premise. Record bibliographic or attribution corrections without failing an argument whose exact mathematics is verified. Missing necessary evidence is inconclusive. An unusable source transcript or evidence response is recorded as `INCONCLUSIVE` with the assigned premises unchanged and no source passages admitted for reuse, so the workflow can continue. Source search has no Xean web-action cutoff; Codex stops naturally when the assigned premises are checked or evidence is unavailable. The separate `review` command audits the complete argument and all supporting claims without trusting solver verdicts; it retains full support and its existing search behavior. Preserve its exact request and transcript in its own journal.

External `verification: {source, report}` is an explicit caller attestation. It establishes a note only over verified support while the note is not dead. Source, correctness, and reconstruction failures retain their normal authority, and every accepted note still needs all four normal verifiers. The attestation's `source` identifies its reviewer or caller, separately from the literature source verifier. The caller owns file conversion, retrieval, dataset analysis, and the selection of prior-run material. The solver accepts text through the existing note graph and support closure.

Derive each inspection from one captured journal entry array. The projection keeps journal facts in maps and derives verified, dead, and accepted in numeric note order, since support always precedes its note. Preserve candidate-bound PASS groups, historical non-requirements failures, and sequence filtering. Support closure has one traversal in `support.ts`, shared by validation, context selection, window calculation, and export. Visit shared ancestors once and memoize eligibility only within a fixed evidence view. Validate dependencies from the structured `support` array, without scanning note text for IDs. Correctness checks for undeclared substantive dependencies over each note's own support closure. Verifier-input validation and verifier prompt construction retain their asynchronous internal boundaries.

Use the current workflow, command, settings, and protocol schemas. Delete retired formats and migration paths. Inspection must reject unsupported declarations instead of treating them as standalone call journals. Reject mismatches without rewriting the campaign. Keep exact request and evidence checks within the current format, one result projection, and resume through the existing `run` command.

Spend reasoning generously and never reason again over what was already reasoned, so no result is verified or derived twice; efficiency work waits for measured spend from real runs.

Use one bounded completion loop for implementation work:

1. Collect known blockers and define the observable success condition before editing.
2. Make one focused edit batch.
3. Run `bun run check`.
4. Run one fresh live smoke only when runtime, prompt, provider, or replay semantics changed.
5. Stage the intended files and freeze the diff.
6. Run one correctness review and one simplification review concurrently against that diff. Give each reviewer the exact frozen patch and completed check summary. Reviewers inspect that evidence only. They do not search memory or rerun tests. Default to Luna at high reasoning.
7. Wait at most five minutes. Correctness, security, regression, and direct user-requirement findings block. Advisory cleanup does not.
8. Repair blocking findings, verify the affected checks, and review only the repair delta when its interaction is local. Repeat the full review only when the repair changes the contract.
9. Commit immediately after the blocking gates pass.

Do not add another review layer, repeat a smoke, or keep manually inspecting the same campaign unless new evidence identifies a distinct risk. Public documentation covers installation, usage, integration, and current contracts. Keep measurements, run logs, internal reviews, and research drafts under `runs/` untracked. Do not push unless the user asks.
