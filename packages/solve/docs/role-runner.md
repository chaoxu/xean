# xean-solve workflow

`xean-solve` runs one workflow from a task to `accepted` or `turn-limit`. This document is the authority on solver behavior: roles, the coordinator loop, verification, the inbox, replay, and inspection. [SPEC.md](../../../SPEC.md) is the authority on the kernel: the campaign artifact, calls and tools, the Pi runner and its submission gate, candidates, and verdicts. The [README](../README.md) lists commands and settings, and [agent usage](agent-usage.md) gives command sequences.

## Roles

One task contains the exact `problem` and `completionCriteria`. Four roles share typed contracts, and the campaign and the standalone role commands use the same ones:

```text
ExplorerInput    -> ExplorerResult
CoordinatorInput -> CoordinatorResult
LiteratureInput  -> LiteratureReport
VerifierInput    -> VerifierResult
```

Explorer, coordinator, correctness, requirements, and reconstruction run through Pi. Literature and source verification run the Codex CLI with web search, and both use the `source` profile. A role call is one logical model invocation, which may include provider continuations, recorded with its request, transcript, and submission. Its prompt is a deterministic function of the role input. A Pi role submits through one tool: `submit_notes`, `submit_coordination`, `submit_verdict`, `submit_statement`, or `submit_proof`. A Codex role submits its final JSON message. The standalone role commands run one role from an input file into a campaign of declaration kind `calls` with the same schemas and journal; they are diagnostics, not a second workflow.

### Notes and verdicts

A note is `id`, `summary`, `text`, `support`, `verdicts`, `verified`, and `dead`, with optional external `verification`. Explorer, a caller, or the literature role supplies the text and names the support: the notes whose results the text uses without proving them. The coordinator writes the summary, the verifiers write the verdicts, and the projection derives the two flags. Original submissions and support edges are immutable. A verifier may approve a local correction by returning the full replacement in `correctedText` on a PASS verdict; the projected `text` then uses that replacement. A replacement clears any older summary, and the next coordinator files a new one; historical filings remain available. Substantial changes require a new note. Notes are numbered `n1`, `n2`, and so on in the order they enter the workflow. Every role receives notes in this one shape. Model prompts omit PASS explanations and omit replacement text from verdict metadata, since full notes already carry the corrected text. FAIL and INCONCLUSIVE reports remain complete; typed inputs, the journal, and inspection retain every report and correction.

A verdict names the verifier that produced it, the note it is about, `PASS`, `FAIL`, or `INCONCLUSIVE`, and a report, with optional `correctedText` on PASS only. It always names a note under verification: support is established and not under review. Verdicts accumulate on the note they name.

The projection is rebuilt from the journal on every derivation and never persisted. It filters evidence by journal sequence and computes the corrected text and flags in numeric note order, one pass, because every support note precedes its dependent note. A note is verified when correctness and source have passed it or the caller supplied external verification, provided every note in its support is verified and it is not dead. A note is dead when correctness, source, or reconstruction failed it or a note in its support is dead; external verification does not override this. A requirements FAIL and an INCONCLUSIVE verdict make nothing dead. A note is accepted when it is verified and all four verifiers have passed it. Completed PASS checks remain established across dispatches. The kernel's candidate status is evidence and decides nothing: acceptance is the projection's query over the verdict rows, including reused checks from earlier candidates, so a replacement `Roles.verifier` must bind its calls and verdicts the same way.

Support closure uses the single traversal in `support.ts`. Explorer support selection, verifier-input validation, verification-window calculation, verifier prompts, and export all use it. The traversal visits shared ancestors once, rejects duplicate IDs, missing notes, and support that does not precede its note, and returns the closure in numeric ID order. Validation reads the structured `support` array and does not infer dependencies from note text.

## Coordinator loop

Every campaign starts with a coordinator call. Its typed `action` selects the next role. With overlap enabled, every verifier action also dispatches Explorer concurrently. The dispatched work settles before control returns to a fresh coordinator call:

```text
coordinator -> explorer   -> coordinator
            -> literature -> coordinator
            -> verifier   -> accepted
                          -> coordinator
```

A turn is one coordinator call and the work it dispatches, including both roles in an overlap. The turn is counted when the coordinator's submission settles, so Explorer retries, the verifications of one dispatch, and a dispatched Explorer preempted by frozen caller notes all stay within that turn. No role has a separate bound. The coordinator input carries no turn count or allowance, so the coordinator never learns the cap.

The allowance is a journaled authorization for turns, outside the frozen task and settings. `init` and `run` grant a fresh campaign twenty turns, or `--turns N`, under the id `initial`. Each allowance records `id`, `turns`, and `afterTurns`, the turns spent before it, and its request is the durable receipt. The effective `maxTurns` is the sum of the recorded allowances, and the fold returns `turn-limit` instead of a coordinator call that would exceed it. `run --turns N --id ID` grants another allowance only to a campaign at `turn-limit` and resumes it. Repeating the same id and count resumes without adding turns, a different count under a known id is rejected, and plain `run` never adds turns. The runner lock fences allowance changes and execution.

The verifier action drains the coordinator's `verify` list in verifications that fit the window. It remains available for other ready notes and for outstanding checks on previously checked notes, without requiring a new note. A requested prefix must contain an outstanding reachable check; a prefix consisting entirely of PASS checks, or blocked by FAIL, is rejected. An INCONCLUSIVE check is preserved on resume of the same dispatch; the coordinator may explicitly request a later retry. Acceptance ends mathematical work even when an unrelated note remains unresolved. In an overlap, the runner cancels Explorer and waits for the owned calls to settle before returning `accepted`.

The literature action runs at most once per campaign to completion: after a search returned a valid report, with or without candidates, the action is unavailable, and a failed search leaves it available.

`accepted` and `turn-limit` are terminal results. `paused`, `call-failure`, and `interrupted` are run outcomes that leave the campaign resumable.

## Explorer

`ExplorerInput` contains the task, one `explorerGuidance` string, every note without its text, and the support notes in full: the coordinator's selected support with its complete closure, each full proof once. Every Explorer call carries the dispatching coordinator's recommendation, joined by any pending external advice. The prompt places the notes and supporting proofs before the changing guidance and ends with the call's response budget. The Explorer chooses the mathematics, splits its work into notes, says in a text when a note meets the completion criteria, and writes no summaries. Advice is fallible: the Explorer may reject it or move beyond a suggested step, and the original task remains its objective.

`ExplorerResult` contains new notes, each a text with its support, and a `solution` boolean. Notes are numbered after those the Explorer received, in returned order, and a note may name an earlier note of the same turn. Support names distinct notes that are not dead. A nonroutine imported theorem is stated as a separate note with its hypotheses, conclusion, and source before another note applies it; both can be submitted in the same turn.

### Submissions and continuation

Every Explorer call uses the kernel's submission gate with `completeArgument: "solution"`, `emptyArgument: "notes"`, `maxResponses` from `maxExplorerResponses`, `contextBudgetTokens` from `explorerContextBudgetTokens`, and the continuation prompt `Keep trying, you can do it.`. Explorer calls `submit_notes` once per assistant response with `{notes, solution}`. Each valid submission is validated against the notes known so far, appended as an audited tool call, and answered with a receipt containing only `{noteIds}`; later submissions may name those notes as support. The audited tool-call record is the durable saved submission, even when its receipt or the outer call-result is missing.

The call ends at the first submission with `solution: true`, at the first empty submission, at the response budget, or at the context threshold. A claimed solution hands off early, and the usual verifiers still judge it. The first empty submission hands all saved notes to the coordinator with `emptySubmission: true`, which asks for a different promising approach; the dispatch still spent its turn, and the submission grants no verification status. At the response budget or the context threshold, a valid submission hands all saved notes to the coordinator, and a call that fails there keeps its saved notes.

`maxExplorerResponses` (default 4) is the gate's response budget, which bounds responses, not reasoning tokens or cost. `explorerContextBudgetTokens` (default 400,000) is the gate's context budget. The handoff threshold is the budget minus Pi's 4,096-token safety margin minus the reserve: for `gpt-6-astra` in the pinned Pi registry, whose 272,000-token window caps the budget and whose maximum output tokens are 128,000, the threshold is 272,000 - 4,096 - 128,000 = 139,904 estimated context tokens. The [Pi runner contract](../../../SPEC.md#pi-runner) defines the gate's stopping rule, response and context budgets, reserve, continuation prompt, turn hooks, and recovery.

### Model calls

Every Pi role call sets `maxRecoveries: 8` and `maxLengthContinuations: 8` and a cache key derived from the role label and system prompt. A Pi role profile is `{provider, model, reasoning}` with optional `replayReasoning: false`, which sends every response after the first the transcript without earlier reasoning items; the journal keeps them. The solver's model wrapper applies to every Pi call on the `openai-responses` and `openai-codex-responses` adapters: it requests `auto` transport for `openai-codex-responses` and `sse` for `openai-responses`, disables parallel tool calls and requires the terminal tool, sets `max_output_tokens` for Codex models that support it, and hoists the `openai-responses` adapter's leading developer message into `instructions` before the request is checkpointed.

### Recovery

When a provider fails after making progress within a role call, meaning the last assistant message stopped with an error, an earlier one completed, and no tool result was an error, the workflow derives the unfinished role from the journal and retries it with a fresh provider session and rebuilt input. It permits three such retries between completed role calls, delayed by 1, 2, and 4 seconds. Cancellation, initial-request failures, and invalid tool submissions do not trigger these retries. A fresh Explorer call after failure or interruption receives all notes saved by the interrupted turn in full, with the same IDs and the turn's frozen guidance, and continues numbering after them.

## Coordinator

`CoordinatorInput` contains the task, every note in full including new notes without summaries and dead notes with their verdicts, the `literatureStatus`, the frozen `coordinatorBehavior`, and the optional flag `emptySubmission`. The standalone `coordinator` command defaults the status to `not-started` and the behavior to the default policy.

`CoordinatorResult` files every note without a summary exactly once, lists `verify` entries in priority order, and returns one `action`: `explorer`, `literature` with a discovery request, or `verifier`. An Explorer action also gives `explorerGuidance` and selects `support` notes for Explorer to read in full. A verifier action must supply both fields when overlap is enabled, and omit both when it is disabled. Literature omits them. A verifier action lists at least one note, and the other actions carry an empty list. Each `verify` entry asks for a nonempty prefix of correctness, source, requirements, reconstruction. A listed note is live, and every note in its support is verified or listed earlier with source, so an accepted note's closure is verified by induction. The coordinator asks for correctness and source on a note that later work will build on and all four on a note whose text says it meets the completion criteria.

A summary is for navigation and is never verified: the note's exact statement as a mathematician would state the result, not a description of the note, plus only what the text itself says about its status. It repeats nothing the note's fields say and never judges the text. Guidance recommends useful mathematical work from the recorded evidence and explains the coordinator's uncertainty. The coordinator never asks Explorer to check, polish, or restate a verified note. It has no correctness authority and cannot change verdicts or completion criteria.

### Coordinator behavior

`coordinatorBehavior` is frozen with the settings and appears in every coordinator prompt. `literature` is `optional`, `never`, or `required-if-not-started`, defaulting to `never`; `required-if-not-started` restricts the action to literature while the status is `not-started`, and the literature action is unavailable under `never` or once the status is `completed`. `verification` is `decide` or `always`; `always` restricts the action to verifier and requires listing every unverified live note that has no verdict and whose support is verified, whenever such a note exists, the verifier action is available, and literature is not required first. Under `decide`, the coordinator leaves a note that only cites an external result unlisted until an explorer note names it as support, then lists it with correctness and source before that note. Optional `instructions` add scheduling guidance. The policy cannot change the task, note dependencies, verifier authority, or completion criteria.

`overlap` is a boolean defaulting to `false`. With `overlap: true`, every verifier dispatch pairs with one Explorer turn, under both `verification: "decide"` and `verification: "always"`. The coordinator chooses the role, notes, guidance, and support within the frozen policy. It must include both `explorerGuidance` and `support` in every verifier action. Literature remains serial. The setting is frozen at campaign creation, so changing it requires a new campaign.

### Overlap

An overlap runs Explorer while the existing verifier dispatch drains its list sequentially, including its ordinary window-fitting verifications. A local `xean-solve/overlap` opening freezes the dispatching coordinator's `after` position, the initial Explorer input, and the `verify` list. Explorer keeps those notes, evidence, and guidance on continuation and retry, adding its own saved notes. Concurrent verdicts update the canonical projection immediately. A failed support note makes its dependent notes dead, including dependent notes Explorer submits after the failure.

Each role replays with its own cursor through the durable `xean-solve/overlap-join` boundary. Each verification retains its ordinary local opening and candidate. Caller notes and later guidance wait until after the join. The join is recorded after both roles finish, or after acceptance cancels Explorer and all owned calls settle. Acceptance takes precedence over a concurrent Explorer failure. A nonterminal role failure cancels the other role and waits for both to settle, preserving saved notes and checks. Resume runs only unfinished work. A pause starts no further role calls and lets active calls settle. An interruption signals both roles.

## Literature

The literature role is invoked only by the coordinator action. `LiteratureInput` is the task and the coordinator's request. One focused Codex call with web search returns `{notes}`, a small array of self-contained candidates, each preserving the cited result's hypotheses, limitations, and source details; a candidate's support names an earlier candidate of the same response by one-based position. The runner appends the candidates as a submitted-notes receipt under the id `literature:<call>`, and the ordinary boundary delivers them to the next coordinator input, so the coordinator, Explorer, and verifiers see only notes. They are unchecked until the normal correctness and source checks establish them. A failed call settles the search with no candidates. A cancelled call, or a call whose response is not a valid report, is replaced by a fresh call after the same dispatching coordinator; earlier calls with the same request belong to earlier dispatches and are never reused. The status the coordinator sees is `not-started`, `completed` once any search returned a valid report, or `inconclusive` when searches ran without one.

## Verification

`VerifierInput` contains the task, the `verify` entries of one verification, those notes in full in the listed order, and their complete transitive support outside them in id order. The fold takes the entries as the longest prefix of the coordinator's remaining list whose note and closure texts fit the `window` setting, counting shared texts once and always taking the first entry with its full closure. Before each verification the fold drops entries whose note is dead or whose support is not verified, except support listed earlier with source, so notes blocked by failed or inconclusive support are skipped while independent notes continue. Completed entries leave the list whatever their verdict.

The verifier role submits one kernel candidate for the listed notes and their support, labeled with the verifiers the list asks for, then runs the outstanding verifiers in order. A local `xean-solve/verification` call freezes the exact input and candidate before any check starts. Prior PASS checks are reused; a prior requirements FAIL blocks further completion checks on that note. A later dispatch may retry an INCONCLUSIVE check, while resuming the same dispatch preserves it. Each later check reads the original frozen input with the preceding PASS replacements applied. Each verifier judges the notes that asked for it, passed every verifier before it, and are not dead in the verification. A note is skipped when correctness, source, or reconstruction failed it or a note in its support in the same verification, or when a support note listed in the same verification has not yet passed the verifiers that precede the current one, up to correctness and source, so correctness requires nothing of that support, source requires correctness, and requirements and reconstruction require correctness and source. A note's checks stop at its first verdict that is not PASS. Correctness, requirements, and reconstruction read the closure of just the notes they judge; every inherited dependency is present, and unrelated notes are excluded. Correctness and requirements judge their notes in one Pi call each. Verdict tool schemas use the same note-ID shape for every candidate, and runtime validation requires exactly the judged IDs, once each. Each completed check records one kernel verdict on the candidate, PASS only when every judged note passed, whose evidence lists the note verdicts; a call that already has a verdict is not recorded again. The Pi verdict calls share one system prompt, and calls that judge the same notes begin with the same task, support, and note text, so a provider can serve that prefix from cache; only the verifier name and obligation at the end differ, and the reconstruction judgment appends its statement and proof after them. Every verifier may return INCONCLUSIVE: that completes the check's attempt, leaves the note unaccepted, and preserves the full report for Explorer and the coordinator. Malformed Pi results and provider failures are operational errors.

### Correctness

Correctness reads each note's complete proof and its declared support, checks every load-bearing inference and theorem application, and searches for counterexamples and missing cases. A sound partial result passes even when the task remains unfinished; only requirements judges completion. An application of a nonroutine external theorem must name a support note stating that theorem, and an undeclared substantive dependency fails. An isolated theorem note may cite its source directly and passes conditionally, pending source validation. For every note, correctness lists its exact nonroutine external premises in `externalResults`, each with hypotheses, conclusion, source identification when present, and the claimed application; `[]` means the note relies only on its own proof, its declared support, and routine facts. Premises supplied by declared support are not repeated.

All verifiers and the independent review apply one correction policy. PASS is allowed for a local mistake or omitted routine justification when the reviewer explicitly states and verifies the correction in its report, preserving the note's conclusion and the task's hypotheses, required conclusion, computational model, and bounds; an algorithmic correction verifies soundness, completeness, and running time. Substantial new reasoning, an unsupported essential premise, weakened conclusions, added hypotheses, and undemonstrated repairs fail. Uncertainty without an established blocking defect is INCONCLUSIVE. A solver verdict requiring a local correction also returns the complete approved replacement as `correctedText`, preserving declared support, definitions used by dependent notes, and already established external premises. It introduces no unchecked premise. The original text and every replacement remain in the journal. Each later check within the same dispatch reads preceding approved corrections; subsequent roles, inspection, and export use the corrected text. Reconstruction's independent proof still receives only the statement and support, never the target note or its correction history. A substantive correction requires a new note and fresh checks.

### Source

Source uses the completed correctness submission that established each note's correctness, including a reused submission from an earlier dispatch. Notes whose correctness verdict listed no external premise receive a local PASS in a journaled call with no model request, bound to that correctness call and the current candidate. Remaining notes sharing the same correctness call go to one Codex call with web search. Its packet contains the corrected note texts with their support IDs, each note's assigned premises under per-call IDs formed from the note and the one-based position, such as `n4#1`, and any previously inspected passages; established support proofs are omitted. The Codex output schema enumerates the call's premise IDs, each verdict's `sources` entries bind to them by `resultId`, and the journal restores the assigned premise text behind each ID.

Source opens primary sources, checks the exact statement and its applicability, and returns one verdict per judged note. PASS requires a passage for every assigned premise of the note. Missing necessary evidence is INCONCLUSIVE. A mismatch fails only when it exposes a mathematical defect or an unsupported required premise; a bibliographic or attribution correction is recorded without failing verified mathematics. Xean counts the searches in the transcript and does not check URLs or quotations against opened pages, so they remain model judgments preserved for inspection.

The Codex response requires every schema field, including `correctedText`: a complete replacement on PASS when needed, otherwise `null`. The raw response remains in the call transcript; decoding removes a null correction before evidence checks and journal verdicts. Local source conclusions and Pi verdicts use the optional correction field.

Passages from recorded PASS verdicts of completed source calls earlier in the same campaign are supplied for an assigned premise with exactly the same result text, under the current call's ID and with the call and note that inspected them; the current call still checks applicability. Without a search, every returned passage must exactly match a supplied passage in result, source, URL, and quote. A note whose passages do not bind to its assigned IDs, or without a search do not match supplied evidence, records INCONCLUSIVE for that note alone with its premises unchanged and no passages admitted for reuse; the other notes' verdicts stand. A response that is not one verdict per judged note, or a malformed transcript, records INCONCLUSIVE for every judged note, so the workflow continues. Provider errors and cancellation remain operational failures.

Source has no Xean web-action cutoff: Codex searches until every assigned premise is checked or necessary evidence is unavailable. Codex's informational compaction warnings and reconnect notices do not invalidate an otherwise valid transcript. Every Codex request freezes `search: true`. The process runs in a fresh `CODEX_HOME` with a read-only sandbox and inherits only the selected custom provider's connection settings and named credential variables, or the native login when no custom provider is selected; user instructions, tools, hooks, and rules are excluded. Native Codex usage is journaled without a price.

### Requirements

Requirements decides whether each note meets every completion criterion of the exact task. A sound partial result that does not meet them fails, and a requirements FAIL leaves the note verified but not accepted.

### Reconstruction

Reconstruction is three Pi calls per note, bound to the same candidate. The statement call reads the note and its support and returns what the text establishes, one or several propositions, with nothing of how. The proof call receives the task, that statement, and the support notes in full, never the note's text, and returns a proof that says what it leaves unproved. The judgment call compares the note's text with the proof and returns `statement: null` and one verdict: PASS when both establish the statement and the note uses nothing beyond its support and hypotheses, FAIL when the statement remains unproved after permitted local corrections or the note relies on an undeclared substantive result, INCONCLUSIVE when the independent proof left something unproved and no concrete defect in the note was found. If the extracted statement misstates the note or reveals its method, the judgment returns a corrected `statement` and an empty `verdicts` list, making no verdict. The next proof call reads that correction and the same support, and both requests name the preceding judgment, so resumption selects the correct proof and correction. One such retry is automatic after a fresh correction; a second fresh correction is journaled and ends the call as a resumable failure. Reconstruction runs one note at a time, and a note whose support failed reconstruction earlier in the same verification is skipped. A reconstruction PASS ends the verifier role at once.

### Acceptance and resumption

A verification interrupted after some calls resumes on the same candidate and makes only the calls still missing. Recorded checks, including INCONCLUSIVE ones, are preserved, and a settled call whose kernel verdict was not recorded is recorded on resume. Once every reachable check has a verdict, control returns to the coordinator. A note that has passed all four checks over verified support ends the campaign as `accepted`, including checks reused from earlier dispatches.

## Inbox

An inbox holds caller input in the campaign until a boundary freezes it into the next role input. There are two: submitted notes for the next coordinator input and guidance for the next Explorer input. Each has a receipt label and a boundary label. Receipts and boundaries are local kernel calls with no provider request, and the call request is the durable receipt, including when the submitting process stops before its call-result. Submitters share the `.inbox.lock` file next to the campaign, a short exclusive lock that makes an id unique without blocking the runner, which holds its separate `.runner.lock`. Neither lock file holds campaign state. Reusing an id with identical content returns the original receipt, and different content under the same id fails. A receipt is its request plus `call` and `atMs`.

### Submitted notes

`submit` appends `{notes: [{text, support, verification?}]}` as a `xean-solve/notes` call with request `{schemaVersion: 1, id, notes}`. Every text is stored exactly. String support IDs name distinct existing campaign notes that are not dead, checked against the journal prefix captured for validation; the append retries when the journal grows during validation. Positive integers name earlier notes of the same submission, counted from 1, and self references, forward references, and duplicates are rejected before appending. An optional `verification: {source, report}` is the caller's explicit external verification: `source` identifies the reviewer or caller, separately from the source verifier, and `report` gives its basis. The projection then treats the note as established over verified support while it is not dead. This creates no verifier verdict and cannot accept the campaign, so a supplied complete proof still needs all four verifiers. They can accept it after one turn, its verifier dispatch, with no Explorer call when overlap is disabled.

The boundary `xean-solve/coordinator-notes` freezes pending receipts with `{schemaVersion: 1, after, through}`: `after` is the journal position the next role input derives from, and `through` is the last entry of the snapshot. A boundary includes the receipts after the previous boundary's `through` up to its own, freezes once per position, and refuses when nothing is pending or an Explorer call, a coordinator call, or either boundary has already started after `after`. The runner freezes notes before a coordinator input and before an Explorer input; in the Explorer phase a freeze returns control to the coordinator with the new notes, spending the dispatch's turn. Notes submitted during a literature or verifier role wait for the coordinator input after it. During an overlap they wait until its join, and Explorer alone assigns new note IDs before that boundary. The fold assigns IDs in submission order after the notes present at `after` and resolves local references then, so notes received during an Explorer call are numbered after its returned notes. Frozen role inputs stay unchanged, later submissions wait for another boundary, and a terminal campaign retains later submissions as pending. The coordinator files submitted notes and chooses their verification or use through its ordinary schema; a submission without `verification` starts unchecked. The caller owns file conversion, retrieval, dataset analysis, and prior-run selection, and it preserves separate theorem and proof notes with their edges when transferring a graph, since one text with empty support loses those dependencies.

### Guidance

`guide` appends `xean-solve/guidance` with request `{schemaVersion: 1, id, text}` without checking or changing the workflow phase. Advice on a terminal campaign remains pending, and `guide` never reopens a campaign or changes its result. Before an Explorer turn with pending advice, the runner records `xean-solve/explorer-guidance` with `{schemaVersion: 1, after, through}` under the same boundary rules. The fold joins the advice frozen at that boundary after the coordinator's `explorerGuidance`, in journal order and separated by blank lines, into the Explorer's single `explorerGuidance` string. Advice applies to that turn only, including every retry of it. Advice arriving after the boundary waits for a later turn, and no boundary is recorded when nothing is pending. Guidance cannot establish a note, change a verdict, or add turns.

## Replay and resume

The fold, `deriveWorkflow`, starts from the declared task and settings, derives each role input, and matches the journal's calls to the requests it derives. Explorer and coordinator calls match by system prompt, prompt, and submission gate. The local opening of each verification matches its exact frozen input, including requested checks and prior evidence, and supplies the candidate. Verifier calls match their candidate and exact requests after applying preceding corrections; a source call also matches its assigned correctness submission, exact premises, and supplied passages, and a local source conclusion matches its own exact request. A same-label call after the cursor whose request differs is journal corruption, and the fold refuses it rather than running the role again. Workflow semantics read role calls and receipts, never provider checkpoint payloads.

`run` creates a campaign or resumes one after matching the exact task and settings against its declaration; a disagreement is an error, and unsupported declarations are rejected. Before a fresh campaign or an unfinished resume makes a model call, `run` resolves every configured Pi role and its reasoning level, checks provider credentials, and checks the Codex CLI and its credentials; these checks make no paid model request. A campaign already at a terminal result returns before provider initialization. The runner lock allows one process per campaign. Repeating `run` invokes unfinished work and preserves completed calls, including either completed role of an overlap. On a completed campaign it makes no model request. One `SIGINT` or `SIGTERM` pauses after active role calls settle, and a second interrupts them.

## Independent review

`review` runs one full Codex audit of the exact task and a complete argument, including supporting proofs and citations, with web search and no solver verdicts. It lists every nonroutine external result with its source passages, checks primary sources under the source rules, applies the correction policy, and returns PASS, FAIL, or INCONCLUSIVE with its evidence; citation corrections alone do not change the verdict. Its journal is a separate `xean-review` campaign whose declaration freezes the task, argument, profile, instructions, and output schema, and it records the Codex transcript and passages. A PASS requires a passage for every listed external result, and a review that cites passages without a search is an error. Repeating a completed review returns its original receipt without a model call, and changed inputs or instructions require a new journal. A failed or inconclusive review leaves the solver's acceptance record intact.

## Inspection and export

`inspect` derives everything from one captured journal entry array, so a concurrent append cannot mix journal prefixes in one report. It reports the task, `maxTurns` and the `allowances`, the current phase, notes with verdicts and flags, every role call once with its kernel state, provider outcome, saved error, and submission, spend derived from request completions, and `accounting` with `measuredCostUsd`, `complete`, `unmeasuredRequests`, `unaccountedCalls`, `potentialRequests`, and `unpricedCalls`. Codex calls are unpriced, so a campaign with a source or literature call keeps accounting incomplete. Pi outcomes and accounting use compact call results without reading response or transcript attachments. A terminal campaign adds `result`, and an unfinished campaign reports its next phase. `--include-requests` adds each call's exact request. `--include-guidance` adds each guidance receipt with `calls`, the Explorer calls whose inputs included it, and `pending`. `--include-submissions` adds each notes receipt with `pending`, its `boundary` call, the first `coordinatorCall` after that boundary, and `noteIds` once assigned; a started coordinator request establishes delivery, including one that later fails. Inconclusive reports remain on their notes as the workflow advances. `inspect` lists the notes saved by an Explorer call that has not settled or that failed. `inspect` makes no model call.

During an overlap, `phase` is `overlap` and the report includes `overlap` with `after`, `opened`, `explorerPending`, `verifierPending`, and `acceptedNote` when available. The role calls and spending use the ordinary inspection fields. A resumable run still reports its phase in the execution report's `at` string.

`export` emits the corrected text of the accepted note preceded by its corrected support closure in id order, each under a heading `--- id ---`. Original submissions remain available in the journal.
